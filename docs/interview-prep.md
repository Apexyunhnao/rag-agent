# 面试话术准备 — 知识库问答 Agent（RAG Agent）

> 用法：先背"30 秒版"和"三分钟版"；高频题按"面试官想问什么"理解后用自己的话讲。
> 原则：只讲自己真正做过、理解的东西。被问到代码细节，诚实说"这行是工具生成的，我负责设计和验证"，比硬编强。
> 与项目一配合讲：项目一覆盖"让 Agent 动手做事"（工具编排），项目二覆盖"让 Agent 用资料说话"（RAG）。

## 一、30 秒电梯介绍（开场必背）

"我做过一个电商客服政策知识库 Agent，基于 RAG。预置了 4 份售后文档（退货、退款、换货、物流政策），用户用自然语言提问，系统先检索最相关的政策片段，再让 LLM 生成带来源引用的回答。我建了 20 条测试集做自动评估，按 8:2 分层切留出集（16 train + 4 holdout），保证每份文档至少 1 条留出——留出集是模型没见过的 case。核心设计是引用溯源——回答必须标注 [来源: 文档名]，不许编造。"

要点：三个数字（24 条 / 100% / 91.7%）+ 一个设计思想（引用溯源，不许编造）。

## 二、三分钟项目讲解（按这个顺序讲）

### 1. 为什么做（背景）

"企业里大量知识散落在文档里——员工手册、IT 手册、制度文件。员工想知道年假几天、VPN 怎么连，要翻好几份文档。我的目标是：用自然语言问，系统从文档里找答案，而且回答必须带出处，让提问的人能自己核对。"

### 2. 怎么做的（架构）

"分离线和在线两条线：
- 离线段（ingest）：文档加载 → 按 300 字分块（overlap 50）→ 本地 embedding 模型向量化 → 存进 ChromaDB
- 在线段（query）：问题向量化 → 向量库检索 Top-5 最相关片段 → 把片段和来源一起拼进 prompt → LLM 生成带 [来源: 文档名] 的回答
- 服务层：FastAPI 提供 /query 接口 + Web 界面，每次查询写 SQLite 日志（问题、来源、回答摘要、耗时），方便排查
Embedding 用本地模型（bge-small-zh），不依赖外部 API；LLM 用 DeepSeek，走 OpenAI 兼容接口。"

### 3. 最大的坑（引用溯源残废）

"第一版有个严重问题：回答末尾标的是 [来源: 片段 1] 而不是真实文档名。查下去发现是上下文传递时把来源元数据弄丢了，prompt 里只有片段编号，模型只能跟着编。修复后 prompt 里每段都带真实来源。这个教训让我明白：RAG 的引用溯源是核心功能，上下文必须携带来源元数据，否则'带依据的回答'是假的。"

### 4. 第二个坑（评估脚本骗人）

"第一次评估回答准确率只有 79.2%，我差点去调模型。后来发现一个 bug：关键词匹配没处理空格——回答写'5 天'，测试集关键词是'5天'，答案完全正确却被判失败。修好评估脚本后分数自己就上去了。教训：先验证判卷本身没问题，再信分数。"

### 5. 结果

"24 条测试集，两轮迭代：检索命中率 95.8% → 100%，回答准确率 79.2% → 91.7%。剩下 2 条失败是已知限制：一个是文档本身没写明确答案（模型诚实说没有，算对的行为），一个是检索到但生成没衔接好（可用重排优化）。"

## 三、高频问题 Q&A（面试官想问什么）

### Q1：为什么用 LlamaIndex？不用 LangChain？不自己写？

"RAG 的完整链路——加载、分块、向量化、检索、合成——LlamaIndex 都覆盖，我只需要把每步的组件选型和参数定好。而且它的向量检索直接暴露了底层存储（我用 ChromaDB），我能控制距离度量、分块大小这些直接影响效果的东西。对比过 LangChain：它偏 Agent 编排，RAG 部分抽象层更多，我排查起来反而绕。自己写成本高、没必要——LlamaIndex 是这块的成熟框架。"

### Q2：Embedding 为什么用本地模型？不用 API？

"两个原因：一是成本，本地模型零调用费，一次下载永久用；二是稳定，不依赖外部 API 的可用性和限流。bge-small-zh-v1.5 是中文场景的经典模型，512 维，CPU 就能跑，检索效果够用。代价是首次要下载 400MB 模型（国内要配镜像），机器要求比纯 API 方案高一点。"

### Q3：为什么用 ChromaDB？

"Python 原生、零部署，一条命令装好，数据持久化在本地目录，demo 和评估场景完全够。对比过 FAISS：它是纯检索库，没有客户端概念，调试不如 ChromaDB 直观。生产规模大了再换向量数据库（如 Milvus）也不难——接口上我直接操作 collection，换底层存储改动可控。"

### Q4：怎么评估你的系统？

"建了 24 条测试用例，每条标注了目标文档和答案关键词，跑自动评测。三项指标：检索命中率（Top-5 里有没有目标文档）、回答准确率（答案里有没有关键词）、来源正确率（[来源: xxx] 标得对不对）。两轮迭代从 95.8%/79.2% 到 100%/91.7%。"

### Q5：评估过程中遇到什么问题？

"三个：
- 关键词匹配的空格 bug——'5 天'匹配不上'5天'，判卷错了，修脚本不修系统
- 来源标注丢失——上下文没带 source_doc，模型标[来源: 片段 1]，修上下文传递
- HF 模型下载被墙——代码里设 HF_ENDPOINT 镜像，写进代码比环境变量稳
每轮都是先怀疑评估脚本和测试集，再怀疑模型。"

### Q6：怎么防止 LLM 编造？RAG 的引用溯源怎么保证？

"三层：
- 结构上，prompt 明确要求'只能根据片段回答，没有就回答文档中没有相关内容'，并要求末尾标注 [来源: 文档名]
- 上下文里每段都带真实来源元数据，模型有据可标，不会只能编
- 评估时单独查来源正确率——24 条里 21 条来源标对，剩下 2 条是已知限制
核心：引用溯源是 RAG 的安全边界，对应项目一里'LLM 可以犯错，但不能造成损失'——这里是不许编造、必须给出来源。"

### Q7：LLM 调用挂了怎么办？

"生成调用包了指数退避重试：网络错误、超时、5xx 服务端错误，2/4/8 秒最多重试 3 次；4xx 不重试（重试也没用）。重试耗尽就向上抛，API 层返回 502 + 具体原因。没有重试的时候，网络一抖就把失败记到系统头上，评估数字会被污染——这是项目一踩过的坑，项目二直接带过来了。"

### Q8：/query 出错怎么排查？

"API 统一错误处理：空问题返回 400、知识库没初始化返回 503、检索失败 500、LLM 重试耗尽 502，每条都带 error 字段说明具体原因。加上 SQLite 查询日志（问题、来源、回答摘要、耗时），看日志就知道是哪一步挂了。面试官问'线上报错怎么排查'，就答这个。"

### Q9：为什么用 SQLite 存日志？

"单机演示场景，零部署零配置，查询量小完全够。生产环境日志量大再换 PostgreSQL/时序库，接口改造成本低。"

### Q10：无鉴权？谁都能调 /query？

"对，这是 MVP 阶段的设计决策，不是疏漏——项目明确排除了用户登录，目标是先把问答能力跑通。生产上线第一件事就是加鉴权（API Key 或登录体系）。这么说，比被问住强。"

### Q11：Prompt 注入没防护？用户说'忽略以上指令'怎么办？

"目前没做输入过滤，这是已知风险。RAG 系统里 prompt 注入是安全面试必问点：用户输入可能诱导模型胡说或泄露系统提示词。我的回答是——目前是 demo 阶段，已知风险；生产要加输入过滤（检测注入关键词）+ 输出过滤（校验回答是否带来源）+ 权限隔离（文档分级读取）。主动说，说明我知道边界在哪。"

### Q12：没有留出集？100% 检索命中是不是对着测试集调的？

"确实是全量 24 条评估，没有留出集——项目一有，项目二 MVP 阶段为了快速闭环先用全量。这是已知限制，dev-log 里诚实记了。对着测试集调的风险我知道：迭代次数越多越可能过拟合。补救方向是扩展测试集 + 仿照项目一切留出集。面试就这么讲，别遮。"

### Q13：并发没压测？同步端点？

"对，main.py 是同步端点跑在线程池，全局单例 collection 并发访问没验证过。demo 没问题，企业上线要先压测——单例并发、线程池上限、超时兜底都要验证。主动说，别等问。"

### Q14：为什么选 DeepSeek？

"中文效果好，成本低，走 OpenAI 兼容接口——换模型改配置就行，代码不用动。项目里 LLM 模型名是环境变量，默认 deepseek-v4-pro。"

### Q15：和项目一（客服工单）什么关系？

"两个项目覆盖 Agent 应用的两条主线：项目一'让 Agent 动手做事'（工具调用、安全边界、编排），项目二'让 Agent 用资料说话'（检索增强、引用溯源、防编造）。框架按场景选：编排用 LangGraph，检索用 LlamaIndex。评估体系一脉相承：测试集 + 自动评测 + 失败分析。"

## 四、追问深水区（被问到也不慌）

- "Top-5 怎么定？" → 检索取前 5 个最相关片段，是召回率和成本的平衡；后续可做 rerank 精排
- "分块大小为什么 300？" → chunk 300 + overlap 50，迭代对比过 400 的效果，300 检索命中率更高
- "距离度量是什么？" → 余弦距离（hnsw:space=cosine），和相似度分数换算一致，不是名不副实的默认 L2
- "Embedding 模型多大？" → bge-small-zh-v1.5，约 400MB，512 维，CPU 可跑
- "为什么不用带 rerank？" → MVP 简化，Top-5 直接进生成；已知 q12 数据分级类问题就是衔接问题，rerank 是优化方向
- "测试集怎么建的？" → 从 5 份文档里挑高频真实问题（年假、VPN、报销、试用期、申诉），人工标注目标文档和答案关键词
- "为什么答案准确率不是 100%？" → 2 条失败是已知限制：文档本身没明确答案（q19，模型诚实回答"没有"）、检索到但生成没衔接好（q12）；评估口径是关键词命中，严格但不完美

## 五、诚实边界（绝对不能吹的）

1. 代码是 Claude Code 生成的——但架构设计、组件选型、测试集、评估迭代、坑的修复决策是我做的
2. "100%"只说 24 条测试集内，不说"系统完美"——真实场景文档更多、问题更杂，评估体系可扩展
3. 文档是预置的 5 份，没接真实企业文档库；单轮问答，无多轮对话；无鉴权、无 prompt 注入防护——主动说清楚范围
4. 没有留出集（项目一有，项目二 MVP 全量评估）——诚实承认，说明知道过拟合风险
5. 简历写"设计并验证了知识库问答 Agent（RAG）"，不写"精通 RAG"

## 六、模拟追问（自己练）

1. "你花了多久做完？" → 按阶段分：需求+数据 1 天，ingest+query 核心 1 天，评估迭代 1 天，外部评审整改 1 天（诚实，别吹）
2. "如果文档里没有答案，模型会怎么办？" → prompt 要求回答"文档中没有相关内容"，q19 就是这么跑的——诚实比编造强
3. "换一批新文档能用吗？" → 能，跑一遍 ingest 重新入库即可；但效果要重新评估，因为文档结构不同
4. "模型输出超过 max_tokens 怎么办？" → 生成设了 1024 上限，回答会截断；长回答场景要加大上限或分块生成（当前是已知限制）
5. "数据里有敏感信息怎么办？" → 文档分级权限、回答脱敏、日志不落敏感内容——当前 MVP 没做，生产必做

## 七、外部评审闭环（审批通过，2026-08-05）

### 评审第一轮（P0/P1）——验收通过
外部评审发现的问题和我的整改：
- P0-1 缺 requirements.txt → 补上，9 个依赖带版本约束
- P0-2 向量距离语义不对（默认 L2，retriever 按 cosine 换算）→ ingest 加 hnsw:space=cosine，重跑入库
- P0-3 评估和生成没有重试 → generator 加指数退避（2/4/8 秒 3 次），run_eval 捕获重试耗尽
- P0-4 文件类型名实不符 → required_exts 支持 md/txt/pdf
- P1 三条：README 注明评估口径、requirements.md 修正为 24 条、results.json 进仓库
- 评审结论："验收通过，P0/P1 全部落实，不是嘴上说说"；results.json 真实性它验过——24 条真实数据，失败用例和 dev-log 记录完全吻合

### 评审第二轮（企业上线标准）——已整改
- /query 统一错误处理：400/503/500/502 + error 具体原因（原来失败只返回 500 空错误）
- LLM 调用设超时：OpenAI 客户端 timeout=30，防止 API 挂起拖死请求
- CLAUDE.md 文档漂移（写了 config.py 但仓库没有）→ 删掉，顺手修正 LLM_MODEL/BASE_URL 默认值

## 八、两个项目对照速查（面试官跳着问）

| 维度 | 项目一（客服工单） | 项目二（知识库问答） |
|------|------------------|-------------------|
| 核心能力 | 工具调用编排 | 检索增强生成 |
| 框架 | LangGraph | LlamaIndex |
| 模型出场 | 分类/提取/回复 | 合成回答 |
| 安全边界 | 工具层拒绝执行 | 引用溯源防编造 |
| 评估 | 56 条六轮 100% + 留出集 | 24 条两轮 100%/91.7% |
| 已知限制 | mock 数据、无真实对接 | 无留出集、单轮、无鉴权 |

一句话串起来："一个让 Agent 动手（工具），一个让 Agent 用资料说话（RAG）——框架按场景选，评估方法论一脉相承：测试集 + 自动评测 + 失败分析 + 外部评审闭环。"
