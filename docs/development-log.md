# 开发日志 — 客服售后政策问答 Agent（RAG Agent）

> 记录开发过程中的难点、踩坑、决策与迭代过程。

## 一、项目信息

- 项目：客服售后政策问答 Agent（RAG Agent）
- 技术栈：Python 3.10+ / LlamaIndex / ChromaDB / bge-small-zh-v1.5（本地 embedding）/ DeepSeek（openai SDK）/ FastAPI / SQLite
- 定位：与「客服工单处理 Agent」互补——本项目管理「政策怎么答」，工单 Agent 管「工单怎么办」
- 开发方式：Claude Code 写代码，架构指导与验收由人工把关

## 二、版本演进

- **v1**：知识库是企业办公文档（员工手册、IT FAQ 等 5 份），先把「检索 + 引用溯源」这条链路跑通
- **v2（当前）**：知识库整体重构为电商售后政策 4 份文档（退货 / 退款 / 换货 / 物流配送），同步重建测试集、切留出集、统一评估口径

**为什么重构**：v1 的办公文档场景跟其他项目没有业务关联，单独摆着讲不出链路。换成售后政策后，它正好补上「政策问答」这一环——工单 Agent 处理订单 / 物流 / 售后工单，遇到政策类问题由上游 supervisor 调到本服务。两个项目拼成一条完整的客服链路。

## 三、踩过的坑

### 坑 1：HF 模型下载被墙
- 现象：bge-small-zh-v1.5 模型下载卡死（HuggingFace 直连不通）
- 修复：代码里优先加载 `.env`，`HF_ENDPOINT=https://hf-mirror.com` 在导入 huggingface 之前生效
- 教训：国内环境跑 huggingface 模型，镜像必须在 import 前设置，写进 .env 比每次敲环境变量稳（clone 项目改一处配置就能跑）

### 坑 2：向量距离语义名不副实
- 现象：ChromaDB 默认用 L2 距离，但 retriever 是按 cosine 把 distance 换算成相似度分数的——距离度量和消费端口径不一致，排序不可信
- 修复：建 collection 时显式 `metadata={"hnsw:space": "cosine"}`，与 retriever 的分数换算对齐，重跑入库
- 教训：默认值不等于正确值。距离度量这种直接影响排序的参数，必须显式声明，并和消费端对齐

### 坑 3：评估脚本关键词匹配的空格 bug
- 现象：关键词匹配没做归一化，回答里数字和单位之间带空格时（如「7 天」），匹配不上测试集里的「7天」，答案完全正确却被判失败
- 修复：匹配前归一化——去掉所有空格（含全角）、转小写
- 教训：评估脚本的判定逻辑本身也要验证。先跑已知正确答案的用例，确认判卷没问题，再信分数——否则会去修一个根本不存在的模型问题

### 坑 4：来源标注可能缺失
- 现象：模型偶尔忘记在回答末尾写 `[来源: 文档名]`
- 修复：双保险——prompt 里强制要求；生成后代码层兜底（回答里没出现来源时，自动补 top-1 片段的来源）
- 教训：引用溯源是 RAG 的核心功能，不能只靠 prompt 约束，关键保证要有代码层兜底

## 四、评估设计

- **测试集 20 条**：4 份政策文档各 5 条，覆盖高频真实问题（退货条件、退款到账、换货运费、预售发货…）
- **分层切分**：按 8:2 切（seed=42），16 条训练 + 4 条留出，**每份文档至少 1 条进留出集**（R04 / R09 / R14 / R17）
- **三项指标**：
  - 检索命中率：Top-5 片段里有没有目标文档
  - 回答准确率：回答有没有命中预期关键词
  - 来源正确率：`[来源: xxx]` 标得对不对
- 迭代只用训练集，留出集留到最后验收——避免对着答案调

## 六、失败用例分析（2 条）

两条失败是同一类问题——**文档里没写这个问题的答案**：

- **R10「退款申请后怎么查进度」**：模型回答「文档中没有相关内容」，检索命中和来源标注都正确（命中 退款政策.md）。说明它没有编造，但退款政策文档里确实没写「查询进度」的渠道——这是**知识库覆盖度问题**，不是生成环节的问题
- **R20「能否指定快递公司配送」**：同理，物流配送政策里没写这条规则

处理方向：补文档（把缺失的规则写进政策文档）比调模型更对症。这也是 RAG 的基本功——**答案不准时先看知识库有没有写**，别急着怪模型。

## 七、已知限制（面试主动讲）

1. 知识库只有 4 份政策文档，覆盖面小；文档是预置的，没接真实企业文档库
2. 留出集只有 4 条——每份文档各 1 条，能验证泛化方向，但样本量小，不足以从统计上证明泛化
3. 单轮问答，无多轮对话（「那退款呢」这类指代追问不支持）
4. 无用户鉴权、无 prompt 注入防护、并发未压测

## 八、与客服工单 Agent 的关系（面试素材）

| 维度 | 客服工单 Agent | 本项目（RAG） |
|------|---------------|--------------|
| 核心能力 | 工具调用编排 | 检索增强生成（RAG） |
| 框架 | LangGraph | LlamaIndex |
| 模型出场 | 分类 / 提取 / 回复 | 合成回答 |
| 安全重点 | 工具层边界（拒绝执行） | 引用溯源（不许编造） |
| 评估 | 59 条（47 训练 + 12 留出）多轮迭代 | 20 条（16 训练 + 4 留出） |

一句话：一个让 Agent 动手做事（工具），一个让 Agent 用资料说话（RAG）。上游 supervisor 把两个服务串起来——政策问答交给本服务，工单执行交给工单 Agent。
