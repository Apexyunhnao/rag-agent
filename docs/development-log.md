# 开发日志 — 知识库问答 Agent（RAG Agent）

> 记录开发过程中的难点、踩坑、决策与迭代过程。

## 一、项目信息

- 项目：知识库问答 Agent（RAG 线，项目二）
- 技术栈：Python 3.10+ / LlamaIndex / ChromaDB / bge-small-zh-v1.5（本地 embedding）/ DeepSeek v4-pro / FastAPI / SQLite
- 定位：与项目一（LangGraph 客服工单，编排线）互补，覆盖 RAG 能力线
- 开发方式：Claude Code 写代码，羔丸架构指导 + 验收

## 二、踩过的坑

### 坑 1：HF 模型下载被墙
- 现象：bge-small-zh-v1.5 模型下载卡死（HuggingFace 直连被墙）
- 修复：代码顶部（import 模型前）设置 os.environ['HF_ENDPOINT'] = 'https://hf-mirror.com'
- 教训：国内环境跑 huggingface 模型，镜像必须在 import 前设置，写进代码比环境变量更稳（clone 项目也能跑）

### 坑 2：来源标注丢失（引用溯源残废）
- 现象：回答末尾标注"[来源: 片段 1]"而不是文档名
- 原因：query_pipeline 传给 generator 时只传了片段文本，把 source_doc 丢了，prompt 里只有"[片段 1]"，模型只能跟着标
- 修复：generate 接收 (text, source_doc) 对，prompt 里每段标注真实来源
- 教训：RAG 的引用溯源是核心功能，上下文必须携带来源元数据，否则"带依据的回答"是假的

### 坑 3：评估脚本关键词匹配空格 bug
- 现象：回答"5 天"（有空格）匹配不上关键词"5天"，年假问题回答完全正确却被判失败
- 修复：匹配前归一化（去空格含全角、转小写）
- 教训：评估脚本的判定逻辑要先验证——先跑已知正确答案的用例，确认判卷本身没问题，再信分数

## 三、评估迭代过程

| 轮次 | 检索命中率 | 回答准确率 | 关键动作 |
|------|-----------|-----------|---------|
| 1 | 95.8% | 79.2% | 基线；失败 5 条（含脚本空格误判） |
| 2 | 100% | 91.7% | 修空格匹配 + 分块优化（chunk 300+overlap 50）+ prompt 要求完整列出应对步骤 |

### 第 1 → 2 轮分析
- q01 年假：答案正确但被判失败——评估脚本 bug（空格），修脚本不修系统
- q09 WiFi 密码：检索未命中 IT FAQ——分块优化后解决
- q12 数据分级：检索到但生成没用上（衔接问题）——保留为已知限制
- q15 可疑邮件：检索命中但回答不完整——prompt 加"步骤必须完整逐条列出"后解决
- q19 几点下班：文档本身没明确写，模型诚实回答——测试集/文档问题，保留

## 五、已知限制（面试主动讲）

1. q12 数据分级类问题：检索到相关文档但生成环节未能准确提取——检索与生成的衔接还有提升空间，可用重排（rerank）或更强 prompt 优化
2. 测试集只有 24 条，覆盖有限；文档都是预置的，没接真实企业文档
3. 没有留出集（项目一有，项目二 MVP 阶段用全量 24 条评估）
4. 单轮问答，无多轮对话

## 六、与项目一的对比（面试素材）

| 维度 | 项目一（客服工单） | 项目二（知识库问答） |
|------|------------------|-------------------|
| 核心能力 | 工具调用编排 | 检索增强生成（RAG） |
| 框架 | LangGraph | LlamaIndex |
| 模型出场 | 分类/提取/回复 | 合成回答 |
| 安全重点 | 工具层边界（拒绝执行） | 引用溯源（不许编造） |
| 评估 | 56 条六轮 100% + 留出集 | 24 条两轮 100%/91.7% |

面试话术：两个项目覆盖 Agent 应用的两条主线——"让 Agent 动手做事"（工具）和"让 Agent 用资料说话"（RAG）。框架选型按场景：编排用 LangGraph，检索用 LlamaIndex。
